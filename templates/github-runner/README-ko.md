# 비공개 컨슈머 Actions 러너

`scripts/prepare-self-hosted-ci.mjs`와 테스트를 컨슈머의 `scripts/`로 복사합니다. `ops/github-runner/config.example.json`을 `ops/github-runner/config.json`으로 복사하고 정확한 저장소, 빌더 이름, 호스트와 컨테이너에서 동일한 작업 경로를 지정합니다.

개인 계정은 저장소별 러너 등록이 필요하지만 여러 러너 컨테이너를 Coolify 서비스 하나로 관리할 수 있습니다. 조직 소유 저장소는 조직 러너를 공유할 수 있습니다. 등록 정보, 도구 캐시, 작업 경로는 저장소별로 분리하고 최신 glibc가 필요한 릴리스 도구는 고정된 Ubuntu 24.04 러너 이미지에서 실행합니다.

등록, 온라인 상태와 실제 실행 검증까지 `COOLIFY_RUNNER_ENABLED`를 false로 둡니다. 원래 비공개 저장소와 소유자 본인의 동일 저장소 PR만 자체 러너를 선택합니다. 공개 복사본, 외부 PR, 다른 사용자의 PR과 비활성 상태는 GitHub 기본 러너를 사용합니다. 릴리스와 업로드 권한은 컨슈머 정책을 유지합니다.

자체 러너의 Docker 작업은 checkout과 Node 준비 후 도우미를 실행합니다. CPU 4개·메모리 8GiB로 제한된 별도 Buildx 컨테이너를 만들고 실제 제한과 이미지 로딩을 확인합니다. 서버 기본 빌더를 변경하거나 공유 저장소를 일괄 정리하지 않습니다. 임시 파일은 작업 bind mount 내부의 RUNNER_TEMP를 사용합니다. 테스트용 Docker 실행 함수에 `ciDockerArgs`를 적용하면 CPU 2개·메모리 4GiB로 제한하고 기본 러너 동작을 유지합니다.

호스트 Docker 소켓은 자원 제한과 관계없이 서버 관리 권한을 제공합니다. 기존 Docker 테스트가 호스트 루프백을 사용한다면 러너의 호스트 네트워크가 필요합니다. 다른 러너는 서비스 네트워크를 유지합니다. 준비된 구성의 호스트 접근을 승인받기 전에는 배포하지 않으며 등록 자격 증명을 소스나 로그에 넣지 않습니다.

러너의 실제 CPU·메모리 제한, 라벨, 이미지 로딩, 임시 경로와 재시작 복구를 검증합니다. 네이티브 Rust 작업은 컨슈머 rust-toolchain 파일을 적용하고 SQL 검사는 필요한 경우 SQLite STRICT를 지원하는 Python을 사용합니다. CI 도우미를 적용하기 위해 키트 gitlink, 서버, 데이터 스키마, 릴리스 기준 버전을 변경하지 않습니다.

`runnerService`에는 실제 Compose 서비스 키를 지정합니다. 도우미는 일치하는 러너가 하나인지, 작업 경로가 호스트와 컨테이너에서 동일한 쓰기 가능한 bind mount인지 검사합니다. `hostNetwork`가 true이면 배포 전에 외부 Compose 서비스에 `network_mode: host`를 지정해야 합니다. 도우미는 해당 네트워크 모드를 검증하며 JSON 설정 자체가 네트워크를 배포하거나 변경하지 않습니다.
